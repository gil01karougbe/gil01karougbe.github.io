## Introduction
<p style="text-align: justify;"> Local Shellcode Injection, often called Self Injection, is one of the most basic yet important techniques to understand in Windows malware development and red teaming. Before diving in, it's worth defining what shellcode actually is: <strong>shellcode is position-independent machine code</strong> — raw bytes that perform a specific action when executed, with no dependency on a fixed base address or an import table. This is what makes it portable and embeddable directly inside a running process. The concept is then straightforward: </p>
<strong><em>A process injects and executes shellcode within its own memory space</em></strong><br>
<p style="text-align: justify;"> While the technique itself is not stealthy and is easily detected by modern AV and EDR solutions, it plays a critical educational role. Almost every advanced process injection technique builds upon the same foundations. Understanding self injection is therefore the prerequisite to understanding everything that comes after it.</p>

## Flow
<p style="text-align: justify;"> At a High-Level, in self injection, everything happens inside the same process:
<ol>
  <li>Allocate executable memory</li>
  <li>Copy shellcode into that memory</li>
  <li>Execute the shellcode using a thread</li>
  <li>Wait for execution and clean up</li>
</ol></p>

#### 1. Allocate executable memory
<p style="text-align: justify;">The first step consists of allocating memory within the current process using <code>VirtualAlloc</code>. Let's break down the arguments:
<ul>
  <li><code>NULL</code> — we let the OS pick the base address of the allocation.</li>
  <li><code>sizeof(shellcode)</code> — the size of the region to allocate.</li>
  <li><code>MEM_COMMIT | MEM_RESERVE</code> — reserve a range of virtual address space <em>and</em> back it with physical memory in a single call. Without <code>MEM_COMMIT</code>, the memory is reserved but not usable.</li>
  <li><code>PAGE_EXECUTE_READWRITE</code> — marks the region as readable, writable, <em>and</em> executable (RWX). This is necessary because we first write the shellcode into it and then execute it from the same region.</li>
</ul>
Allocating a <strong>RWX</strong> memory region is already a major detection signal. Legitimate software almost never needs a page that is simultaneously writable and executable. We will revisit this in the Detection section.</p>
```C
LPVOID mem_allocated = VirtualAlloc(
    NULL,
    sizeof(shellcode),
    MEM_COMMIT | MEM_RESERVE,
    PAGE_EXECUTE_READWRITE
);
```

#### 2. Copy shellcode into that memory
<p style="text-align: justify;"> Once the memory is allocated, the shellcode is copied into it using <code>RtlCopyMemory</code> — a kernel-exported wrapper around <code>memcpy</code> that is functionally equivalent here. After this call, the payload exists as raw executable bytes sitting in the allocated memory region, ready to run. Nothing has executed yet; we have only moved bytes into place.</p>
```C
RtlCopyMemory(mem_allocated, shellcode, sizeof(shellcode));
```

#### 3. Execute the shellcode using a thread
<p style="text-align: justify;"> To execute the shellcode, we create a new thread using <code>CreateThread</code> and point its entry point directly at our allocated memory. The key parameter here is the third argument: <code>(LPTHREAD_START_ROUTINE)mem_allocated</code>. <code>LPTHREAD_START_ROUTINE</code> is simply a function pointer type that Windows expects as a thread entry point. By casting <code>mem_allocated</code> — the address of our shellcode — to that type, we are telling Windows: <em>"start a thread here and execute whatever you find at this address."</em> From this point on, the CPU will begin fetching and executing our shellcode bytes as if they were a normal function.</p>
```C
HANDLE hThread = CreateThread(
    NULL,
    0,
    (LPTHREAD_START_ROUTINE)mem_allocated,
    NULL,
    0,
    NULL
);
```

#### 4. Wait for execution and clean up
<p style="text-align: justify;"> After the thread is created, the main thread calls <code>WaitForSingleObject(hThread, INFINITE)</code> to block until the shellcode thread finishes. Without this, the main thread could reach <code>main()</code>'s return and tear the process down before the shellcode completes. Once done, <code>CloseHandle</code> releases the thread handle and <code>VirtualFree</code> releases the allocated memory page — good practice to keep the process clean and avoid memory leaks or leftover indicators.</p>
```C
WaitForSingleObject(hThread, INFINITE);
CloseHandle(hThread);
VirtualFree(mem_allocated, 0, MEM_RELEASE);
```

## Detection Perspective (Blue Team Insight)
<p style="text-align: justify;">
As discussed earlier, self injection is not opsec safe at all. Let's look at the two most obvious detection points and how they can be partially mitigated.
</p>

<p style="text-align: justify;">
<strong>1. Shellcode stored in plaintext.</strong> The raw shellcode bytes sit statically inside the binary, making them trivially detectable by signature-based scanners. To reduce this, the shellcode can be encrypted (XOR, AES, …) or obfuscated and stored inside a PE resource section. At runtime the loader decrypts it into memory before use — meaning the static bytes on disk never match a known signature.
</p>

<p style="text-align: justify;">
<strong>2. RWX memory allocation.</strong> Allocating a page with <code>PAGE_EXECUTE_READWRITE</code> is one of the most reliable injection indicators that EDRs and memory scanners look for. Legitimate software almost never needs a region that is simultaneously writable <em>and</em> executable. The fix is to separate the two operations: allocate with <code>RW</code> permissions first, copy the shellcode in, then call <code>VirtualProtect</code> to flip the region from <code>RW</code> to <code>RX</code> (read + execute only) before creating the thread. At no point does the page hold all three permissions at once, which removes that specific detection signal — though the transition itself is still visible to a vigilant EDR.
</p>
