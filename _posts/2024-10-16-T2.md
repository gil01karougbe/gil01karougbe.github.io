## Introduction
<p style="text-align: justify;"> Remote Process Shellcode Injection is the natural evolution of self injection (T1). Instead of running shellcode inside the current process, we inject and execute it inside a different, already-running process on the system. This has a meaningful operational impact: the malicious activity appears to originate from a legitimate process (such as <code>notepad.exe</code> or <code>explorer.exe</code>), and the loader is cleanly separated from the payload — if defenders notice something suspicious, they are looking at the target process rather than ours. The concept is: </p>
<strong><em>A process allocates memory inside a remote target process, writes shellcode into it, and triggers execution via a remote thread</em></strong><br>
<p style="text-align: justify;"> Compared to T1, we now cross a process boundary. Every Win32 API that previously operated on the current process has a cross-process counterpart: <code>VirtualAlloc</code> becomes <code>VirtualAllocEx</code>, <code>CreateThread</code> becomes <code>CreateRemoteThread</code>. We also gain two entirely new steps: locating the target process and obtaining a handle to it.</p>

## Flow
<p style="text-align: justify;"> At a high level, remote injection follows these steps:
<ol>
  <li>Find the target process PID</li>
  <li>Open a handle to the target process</li>
  <li>Allocate memory inside the target process</li>
  <li>Write shellcode into the target process</li>
  <li>Execute the shellcode via a remote thread</li>
  <li>Wait for execution and clean up</li>
</ol></p>

#### 1. Find the target process PID
<p style="text-align: justify;"> Before crossing the process boundary, we need to know which process to target. Windows provides a snapshot API for this: <code>CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0)</code> takes a point-in-time snapshot of all running processes and returns a handle to it. We then iterate over every entry with <code>Process32First</code> and <code>Process32Next</code>, comparing <code>pe32.szExeFile</code> (the executable name) against our target string. When we find a match, we record the PID and stop. Note that <code>pe32.dwSize</code> must be set to <code>sizeof(PROCESSENTRY32)</code> before the first call, or the API will fail.</p>
```C
PROCESSENTRY32 pe32;
pe32.dwSize = sizeof(PROCESSENTRY32);

HANDLE hSnapshot = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);

Process32First(hSnapshot, &pe32);
do {
    if (strcmp(pe32.szExeFile, "Notepad.exe") == 0) {
        pid = pe32.th32ProcessID;
        break;
    }
} while (Process32Next(hSnapshot, &pe32));
CloseHandle(hSnapshot);
```

#### 2. Open a handle to the target process
<p style="text-align: justify;"> With the PID in hand, we call <code>OpenProcess</code> to obtain a kernel handle to the target process. The first argument specifies the access rights we are requesting — <code>PROCESS_ALL_ACCESS</code> asks for the broadest possible set of permissions, covering the right to allocate memory, write to it, and create threads inside the target. In real-world scenarios, requesting only the minimum necessary rights (<code>PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_CREATE_THREAD</code>) is less suspicious: requesting <code>PROCESS_ALL_ACCESS</code> on a sensitive process is itself a detection signal that EDRs actively watch for.</p>
```C
HANDLE hProcess = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
```

#### 3. Allocate memory inside the target process
<p style="text-align: justify;"> <code>VirtualAllocEx</code> is the cross-process version of <code>VirtualAlloc</code>. The additional first argument — the process handle — tells Windows to perform the allocation inside that process's virtual address space rather than our own. All other parameters carry the same meaning as in T1: we reserve and commit a RWX page large enough to hold the shellcode. The returned pointer is an address <em>in the target process</em>, not in ours.</p>
```C
LPVOID mem_allocated = VirtualAllocEx(
    hProcess,
    NULL,
    sizeof(shellcode),
    MEM_RESERVE | MEM_COMMIT,
    PAGE_EXECUTE_READWRITE
);
```

#### 4. Write shellcode into the target process
<p style="text-align: justify;"> <code>WriteProcessMemory</code> copies our shellcode bytes from our process into the allocated page inside the target process. The second argument is the destination address (in the target's address space — the pointer returned by <code>VirtualAllocEx</code>), the third is our local shellcode buffer, and the fourth is the byte count. After this call, the shellcode lives inside <code>Notepad.exe</code>'s memory. We have not executed anything yet — we have only moved bytes across the process boundary.</p>
```C
WriteProcessMemory(hProcess, mem_allocated, shellcode, sizeof(shellcode), NULL);
```

#### 5. Execute the shellcode via a remote thread
<p style="text-align: justify;"> <code>CreateRemoteThread</code> is the cross-process counterpart to <code>CreateThread</code>. By passing <code>hProcess</code> as the first argument, we instruct Windows to create the new thread inside the target process rather than our own. The entry point is cast to <code>LPTHREAD_START_ROUTINE</code> and points to the shellcode we just wrote — exactly as in T1. From this moment, <code>Notepad.exe</code> has a new thread running our shellcode under its identity.</p>
```C
HANDLE hThread = CreateRemoteThread(
    hProcess,
    NULL,
    0,
    (LPTHREAD_START_ROUTINE)mem_allocated,
    NULL,
    0,
    NULL
);
```

#### 6. Wait for execution and clean up
<p style="text-align: justify;"> We wait for the remote thread to complete with <code>WaitForSingleObject</code>, then release resources in the correct order: <code>VirtualFreeEx</code> frees the allocated page inside the target process (note the <em>Ex</em> suffix — we are freeing memory that belongs to another process), then we close the thread handle and finally the process handle. Closing in this order matters: closing the process handle first could invalidate the thread handle before we close it cleanly.</p>
```C
WaitForSingleObject(hThread, INFINITE);
VirtualFreeEx(hProcess, mem_allocated, 0, MEM_RELEASE);
CloseHandle(hThread);
CloseHandle(hProcess);
```

## Detection Perspective (Blue Team Insight)
<p style="text-align: justify;">
Remote injection introduces several new detection surfaces on top of the RWX allocation signal from T1.
</p>

<p style="text-align: justify;">
<strong>1. Cross-process memory operations.</strong> A call to <code>VirtualAllocEx</code> or <code>WriteProcessMemory</code> targeting a PID that does not belong to the calling process is a strong injection indicator. Legitimate software almost never writes into another process's memory space. EDRs hook these APIs and flag any such call that originates from an untrusted process.
</p>

<p style="text-align: justify;">
<strong>2. CreateRemoteThread.</strong> This is arguably the most reliable injection signal. A thread created in a foreign process by an unrelated caller is virtually always malicious. Modern EDRs treat any <code>CreateRemoteThread</code> call where the caller and target are different images as high-confidence injection. A partial mitigation is to use alternative execution primitives — APC injection (<code>QueueUserAPC</code>), thread hijacking (<code>SuspendThread</code> + <code>SetThreadContext</code>), or early-bird injection — which achieve the same result without the obvious <code>CreateRemoteThread</code> call.
</p>

<p style="text-align: justify;">
<strong>3. PROCESS_ALL_ACCESS.</strong> Requesting <code>PROCESS_ALL_ACCESS</code> via <code>OpenProcess</code> on a common process (like <code>notepad.exe</code> or <code>explorer.exe</code>) from an unrelated binary generates a kernel audit event. Requesting only the minimum necessary access rights makes the handle request appear less anomalous.
</p>
