## Introduction
------------------------------------------------------------------------------------------
[hammer](https://tryhackme.com/r/room/hammer) is a medium-rated Linux box from TryHackMe. The exploitation starts by abusing the password reset functionality to enumerate valid email addresses. From there, we brute-force the MFA code, which gives us the ability to reset the target user's password. Once logged in, we abuse the JWT to escalate our privileges to admin within the application, unlocking full access to the command execution feature.

------------------------------------------------------------------------------------------

The logs expose a failed authentication attempt: `tester@hammer.thm` tried to access a restricted area with the wrong password. That gives us a valid username to work with.
```
tester@hammer.thm
```
![logs3](../assets/img/ctf/tryhackme/hammer/hammer10.png)
![logs3](../assets/img/ctf/tryhackme/hammer/hammer11.png)
Notice the "Invalid email address!" error on the reset password page — this response difference is exactly what makes email enumeration possible. The application is leaking information by responding differently depending on whether the email exists or not.

Let's confirm by submitting the email we found in the logs.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer12.png)
Entering `tester@hammer.thm` on the reset password page produces a different response, confirming it is a valid account in the system.

It is also worth noting that we could fuzz for other valid emails using this same difference in responses. Let's try that.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer13.png)
![logs3](../assets/img/ctf/tryhackme/hammer/hammer14.png)
There is rate limiting in place — but that is not going to stop us. The first question to ask is: what does the server actually track to count our attempts? After some testing, it turns out the server is tracking the unauthenticated session cookie.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer15.png)
Once we remove the `Cookie` header from the request, the `Rate-Limit-Pending` header in the response always resets to 9. This means the server has no reliable way to track us without a session, giving us a wide-open window to fuzz freely.
```text

User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:109.0) Gecko/20100101 Firefox/115.0
```

```bash
ffuf -c -request reset_pass.req -request-proto http -w usernames.txt -fs 1754
```
![logs3](../assets/img/ctf/tryhackme/hammer/hammer16.png)
The fuzzer confirms `tester@hammer.thm` again. Either way, we now have a valid target email and two possible paths forward:

- Brute-force `tester@hammer.thm`'s password on the login page
- Attack the MFA flow to reset the password directly

![logs3](../assets/img/ctf/tryhackme/hammer/hammer17.png)
Looking at the MFA page, a few things stand out:
- There is rate limiting on code submissions.
- There is a countdown timer — the user has 175 seconds to enter a valid MFA code.
- If the countdown reaches 0, the server redirects to a "Time elapsed" error page.

Unlike the email enumeration step, we cannot simply drop the session cookie here. Without it, the server immediately redirects us to the same "Time elapsed" error page.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer18.png)
![logs3](../assets/img/ctf/tryhackme/hammer/hammer19.png)
The key insight is: if we can find a request parameter that tricks the server into thinking each request comes from a different source, we can bypass the rate limit and brute-force the 4-digit MFA code within the 120-second window.

After researching "Rate Limit Bypass" techniques, one common approach stands out.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer20.png)
The `X-Forwarded-For` header works here. Each time we change the IP value in this header, the server grants us a fresh batch of 10 requests. To brute-force a 4-digit code (up to 9000 attempts), we need up to 900 unique IPs.

The loopback range `127.0.0.0/8` gives us more than enough addresses.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer21.png)
![logs3](../assets/img/ctf/tryhackme/hammer/hammer22.png)
```bash
echo '0000' > w.txt
seq 1000 9999 >> w.txt
```
We need 1000 IPs from the loopback range. A bit of subnet math helps here: we need 2^10 = 1024 addresses, so a `/22` subnet (32 − 10 = 22) gives us exactly that.
```bash
prips 127.0.0.0/22 > ip.txt
awk '{for(i=1; i<=9; i++) print $0}' ip.txt > wordlist.txt
```
We then use a Pitchfork attack in ffuf, pairing each MFA code with a different IP address to stay under the rate limit:
- Copy the `PHPSESSID` from your browser and paste it into `mfa_brute.req`
- Submit the target email on the reset page to start the MFA timer
- Launch the Pitchfork attack before the timer runs out

![logs3](../assets/img/ctf/tryhackme/hammer/hammer23.png)


```bash

```
![logs3](../assets/img/ctf/tryhackme/hammer/hammer25.png)
The valid code is the first one that does not match our response size filter — everything else is a rejection page of the same size.

Using that code brings us to a page where we can set a new password.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer26.png)
After setting a new password, we can log in as `tester@hammer.thm`.
![logs3](../assets/img/ctf/tryhackme/hammer/hammer27.png)

## Kill Chain Summary
1. Email enumeration through the reset password functionality.
2. MFA code brute-forcing to reset the `tester@hammer.thm` password.
3. JWT attack to gain admin access within the application.
